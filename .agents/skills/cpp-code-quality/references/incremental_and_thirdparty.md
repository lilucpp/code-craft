# 增量检查机制与三方库隔离指南 (Incremental & Third-party)

在历史遗留项目（Legacy Codebase）或引入大量三方库的现代 C++ 工程中，如何保证**“新代码高标准，老代码零破坏，三方库零骚扰”**？

---

## 一、 童子军法则与增量检查哲学

> “离开营地时，让营地比你来时更干净一点，但不要把整个营地一把火烧了。”

* **老项目全量执行的灾难**：
  * 全量格式化会导致成千上万行改动，彻底破坏 `git blame`（追溯作者成本极大），合并冲突概率极高；
  * 全量静态分析会刷出几千条历史警告，导致团队疲惫直接废弃工具。
* **增量模式的价值**：
  * **行级精准治理**：谁修改代码，谁负责把自己改动的那几行排版好并修复新增缺陷；
  * 未改动的老代码哪怕缩进不对、存在轻微异味，也绝不触碰。

---

## 二、 增量检查的两大技术支柱

### 1. 行级格式化：`clang-format-diff`
* **工作机制**：
  `clang-format-diff` 解析 Unified Diff 格式的文本流（`git diff -U0`），计算出受影响的文件和行号范围（`-lines 12:25`），**仅对目标行施加格式化**。
* **命令范式**：
  ```bash
  # 格式化当前工作区已暂存（git add）的代码行：
  git diff -U0 --no-color --cached | clang-format-diff -p1 -i
  ```

### 2. 头文件告警隔离：`HeaderFilterRegex`
* **工作机制**：
  Clang-Tidy 在分析 `main.cpp` 时，会递归展开其包含的全部头文件（包括 `boost/`, `spdlog/` 等）。
  若未做限制，三方库头文件内部的警告会全部反噬到当前扫描结果中。
* **解决方案**：
  在 `.clang-tidy` 中显式指定正则过滤：
  ```yaml
  # 只有文件路径以 src/ 或 include/ 开头的头文件，其内部警告才会被输出
  HeaderFilterRegex: '^(src|include)/.*'
  ```

## 三、 三方库彻底静音的三重锁

| 层次 | 隔离工具 | 具体实现方式 | 拦截效果 |
| :--- | :--- | :--- | :--- |
| **第 1 锁：格式化排除** | `.clang-format-ignore` | 写入 `third_party/**` 与 `build/**` | 彻底防止对外部库源码文件进行误格式化。 |
| **第 2 锁：AST 语义过滤** | `.clang-tidy` | 配置 `HeaderFilterRegex` | 只检查业务逻辑对三方库的调用，静音三方库自身实现。 |
| **第 3 锁：编译器系统头文件** | `CMakeLists.txt` | `target_include_directories(... SYSTEM PRIVATE ...)` | 编译器直接将该目录提升为与 `/usr/include` 同等级别，自动抑制所有语法警告。 |
