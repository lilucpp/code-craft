# 文本化与应用协议设计规范 (Protocol & Textuality)

> 整理自埃里克·雷蒙德（Eric S. Raymond）《UNIX编程艺术》第5章与第7章。

---

## 一、 为什么坚持“文本流”为通用抽象？

> “当你很想设计一个复杂的二进制文件格式，或一个复杂的二进制应用协议时，通常，明智的做法是躺下来等待这种感觉过去。” —— Eric S. Raymond

1. **绝对透明与零门槛调试**：纯文本流不需要专用的反编译或反序列化工具，仅凭标准工具（`cat`, `head`, `grep`, `awk`, `curl`, `nc`）即可查看与注入。
2. **强化封装**：文本协议限制了密集二进制状态的直接内存复制，倒逼模块间通过清晰的语义接口通信，杜绝内部指针与结构体的隐式依赖。
3. **性能顾虑的解法**：如果担心文本流带宽占用，在传输层之上开启轻量压缩（如 gzip/zstd），压缩后的纯文本往往比紧凑的自定义二进制格式更小、更干净。

## 二、 4 类通用数据文件元格式选型

严禁盲目手写无法被通用工具解析的孤岛格式，必须在以下 4 种成熟范式中选型：

| 格式分类 | 组织方式 | 典型代表 | 最佳适用场景 |
| :--- | :--- | :--- | :--- |
| **1. DSV (定界符分隔)** | 单行一条记录，字段用 `:`、`,` 或 `\t` 分隔 | `/etc/passwd`, CSV, TSV | 扁平、字段固定、需要极高读写性能且常被 `cut` / `awk` 批处理的数据。 |
| **2. RFC 822 / 邮件头格式** | `Header: Value` 键值对，空行后跟 Payload 正文 | HTTP 报文, 邮件, Debian 控制文件 | 具有大量可选元数据、主从结构清晰的协议或清单文件。 |
| **3. INI / 分节区配置** | `[section]` 搭配 `key = value` | Git 配置, Desktop 入口文件 | 层次较浅（<= 2 层）、需要运维人员频繁手动编辑的配置文件。 |
| **4. 层次化结构流** | JSON / JSON Lines / YAML | Web API, 审计日志, 复杂配置文件 | 深层嵌套对象、列表数组，或跨多语言服务间交换的复杂领域数据。 |

## 三、 应用协议设计四大军规

### 1. 行驱动（Line-Oriented）
* 每个命令请求与单行应答必须以统一的行终止符（推荐 `\n` 或兼容 `\r\n`）作为边界。
* 行驱动天然适配操作系统的行缓冲机制，极易编写状态机逐行切分解析。

### 2. 自描述的三位数字状态码
借鉴 SMTP、FTP 与 HTTP 的经典设计，协议应答首字段统一设计为三位十进制状态码：
* **`1xx` (Informational)**：临时应答，操作仍在处理中；
* **`2xx` (Success)**：命令已被接收、理解并成功执行；
* **`3xx` (Redirection)**：需要客户端进一步提供数据或重定向；
* **`4xx` (Client Error)**：客户端命令语法错误、参数缺失或权限不足（临时错误）；
* **`5xx` (Server Error)**：服务器内部崩溃或环境故障（致命错误）。

### 3. 状态显式化（Stateless by Default）
* 协议尽量保持**无状态（Stateless）**：单次请求自包含完成操作所需的全部身份凭证与上下文；
* 若必须维持有状态会话，会话 ID 必须作为协议显式字段传递，严禁依赖底层 Socket 链路隐式绑定。

### 4. 显式心跳与自描述
* 包含长连接的应用协议，必须内置清晰可读的 ping/pong 心跳包；
* 握手阶段支持输出协议版本号与能力列表（Capabilities Exchange），确保未来协议平滑升级。
