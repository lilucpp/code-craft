# 接口契约与高级设计原则 (Interface & Contract Principles)

> 整理自面向对象经典原则与陈皓《一些软件设计的原则》（https://coolshell.org/articles/4535.html）。

---

## 1. 开闭原则 (Open/Closed Principle - OCP)

> “软件实体（类、模块、函数等）应当对扩展开放，对修改关闭。”

### 核心思想与落地准则：
* **对扩展开放**：当业务有新的场景、新的数据源或新的算法诉求时，可以通过新增代码（子类、策略实现、插件）来满足。
* **对修改关闭**：已有经过充分测试验证的核心调度逻辑和基类，无需进行任何代码改动。
* **经典实现手段**：
  * **策略模式 (Strategy Pattern)**：通过向核心服务注入不同接口实现（如 `PaymentStrategy`），取代内部硬编码的 `if-else / switch`。
  * **回调/扩展点 (Callbacks & Hooks)**：类似 C 语言的 `qsort(comparator)`，核心调度只负责骨架，变化部分交由调用方定制。

## 2. 接口隔离原则 (Interface Segregation Principle - ISP)

> “客户端不应该被迫依赖它不使用的方法；多个专用的客户端接口优于一个通用的单一胖接口。”

### 核心思想与落地准则：
* **杜绝巨无霸接口（Fat Interface）**：不要把所有潜在方法硬塞进同一个 `SuperInterface` 中，导致实现该接口的类被迫写大量抛出 `UnsupportedOperationException` 的空桩代码。
* **角色接口划分 (Role Interfaces)**：从**使用方的视角**来定义接口，而不是从**实现方的视角**。
  - 例如：一个只读报表服务只需要一个 `Readable` 接口，绝不要强行让它依赖具备 `create()`, `update()`, `delete()` 权限的完整仓储接口。

## 3. 契约式设计 (Design by Contract - DbC)

> “软件系统中的元素交互，应当如同商业活动中客户与供应商之间的‘契约’，责任与权利对等清晰。” —— Bertrand Meyer

### 契约三大核心基石：

```
[调用前] ===> 前置条件 (Pre-condition)  ：客户的义务，服务商的权利
                   ↓
              [执行核心逻辑]
                   ↓
[调用后] ===> 后置条件 (Post-condition) ：服务商的义务，客户的权利
[全周期] ===> 不变式   (Invariant)      ：对象内部在任何安全状态下必须维持的铁律
```

1. **前置条件 (Pre-condition) —— 客户的义务**：
   * 方法被调用前，调用方必须保证达成的先验条件（例如：参数不得为 null、数字必须 > 0、必须已建立连接）。
   * **好处**：一旦满足前置条件，服务商方法内部**无须过度编写冗余的防御性纠错代码**，前置不满足直接触发快速失败（Fail-Fast）。
2. **后置条件 (Post-condition) —— 提供方的承诺**：
   * 方法执行完毕返回时，服务商保证给出的状态属性（例如：返回的集合绝不为 null、新增记录 ID 必存在）。
   * 调用方可以无条件信任该返回承诺，无需再次校验。
3. **不变式 (Invariant) —— 状态守恒约束**：
   * 在对象的整个生命周期中，只要方法调用结束（无论是读是写），核心业务约束必须始终为真（例如：银行账户余额不得为负、订单总额等于子项金额之和）。

### 子类继承与 DbC 原则：
在派生子类或重写方法时：
* **前置条件只能被削弱，不能被加强**（子类接受的输入不能比父类更挑剔）；
* **后置条件只能被加强，不能被削弱**（子类给出的产出承诺不能比父类缩水）。这正是里氏替换原则（LSP）的数学本质。

## 4. 关注点分离 (Separation of Concerns - SoC)

> “计算机科学中最重要的努力目标之一。将复杂的大问题拆解为独立、正交、较小关注点的组合。”

### 核心思想与落地准则：
* 程序员的短期认知容量是有限的，不能在同一个代码上下文中同时关注业务流转、事务控制、安全鉴权、日志追踪和底层 I/O。
* **实现分离的两大途径**：
  1. **标准化协议与接口**：如数据持久层与业务逻辑层完全通过 Repository 接口分离；
  2. **横切关注点下沉 (Cross-Cutting Concerns)**：利用 AOP、中间件、装饰器模式，将日志审计、耗时统计、权限校验剥离出核心业务函数。

## 5. 惯例优于配置 (Convention over Configuration - CoC)

> “将业界公认的模式和信息作为系统的默认规则，开发者只针对特殊个性化需求编写配置。”

### 核心思想与工程实践：
* **消除配置地狱 (Configuration Hell)**：大量项目死于数百行冗长、模板化的 XML/JSON/YAML 胶水配置文件。
* **惯例化落地**：
  * **目录规范惯例**：如测试用例默认位于 `tests/`，编译输出默认位于 `dist/`，无需显式在配置文件指定。
  * **命名映射惯例**：对象属性名与数据库字段名/JSON Key 一致时自动映射，杜绝冗长的映射配置代码。
  * 只有在偏离公认惯例时，才编写明确的配置覆盖项。
