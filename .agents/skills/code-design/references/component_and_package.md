# 包与组件划分设计原则 (Component & Package Principles)

> 整理自 Robert C. Martin (Uncle Bob) 组件设计原则与陈皓《一些软件设计的原则》（https://coolshell.org/articles/4535.html）。

在中观架构设计中，一个系统是由多个包（Package / Module）或组件构成的。以下三大原则指导**类如何归包、何时拆分包、以及包之间的依赖拓扑构建**。

---

## 1. 共同封闭原则 (Common Closure Principle - CCP)

> “一个包中所有的类应该对同一种类型的变化关闭。一个变化影响一个包，便影响了包中所有的类。一起修改的类，应该组合在一起。”

### 核心思想与工程动机：
* **内聚性的包级别延伸**：CCP 是单一职责原则（SRP）在包/组件维度的投影。
* **防止霰弹式修改（Shotgun Surgery）**：如果一个业务概念调整需要程序员在 10 个不同的包中分别修改代码，说明系统的物理打包严重缺乏内聚。
* **指导策略（把什么放在一起）**：
  * 如果两个类在概念上、业务生命周期上高度黏合，总是因为相同的业务变更而同时修改，它们就必须打包在同一个模块/包内。
  * 发生变更时，修改的影响范围被限制在极小的一个包内，维护成本降到最低。

---

## 2. 共同重用原则 (Common Reuse Principle - CRP)

> “包中所有的类应该被一起重用。如果你重用了其中的一个类，就重用全部。没有被一起重用的类不应该被组合在一起。”

### 核心思想与工程动机：
* **依赖等于全盘买单**：当你依赖了一个包（例如通过 `import` 或 Maven/npm 依赖），在逻辑和物理上你就依赖了该包内的所有类及它们所依赖的下游第三方依赖。
* **避免无妄之灾的回归测试**：如果一个包发布了新版本（哪怕只改了一个你根本用不到的冷门类），依赖该包的客户端通常也不得不升级，并对系统进行昂贵的全量回归验证。
* **指导策略（把什么拆分出去）**：
  * CRP 帮助我们给包“减肥瘦身”。
  * 相互之间没有协同重用关系的类，坚决拆分成独立的细粒度包。

> **CCP 与 CRP 的张力平衡**：
> - **CCP 让包变大**（把相关联的、因相同原因变化的类聚集起来，利于维护者）；
> - **CRP 让包变小**（把未被一起重用的类剔除出去，利于使用者）；
> - 架构设计是在维护者友好与使用者依赖解耦之间寻找平衡。

---

## 3. 无环依赖原则 (Acyclic Dependencies Principle - ADP)

> “包与组件之间的依赖结构必须是一个有向无环图（DAG），在依赖结构中绝对不允许出现循环依赖（Cycles）。”

### 循环依赖的致命危害：
* **“晨醒综合征 (Morning After Syndrome)”**：团队中一旦出现 `包 A -> 包 B -> 包 C -> 包 A` 的环形闭环，任何一个人对包 A 的微小修改，都会级联导致 B 和 C 的重新编译和破坏。所有模块纠缠成一个不可分割的单体。
* **无法独立测试**：你无法单独为包 A 编写单元测试，必须把 B、C 整个环境全部拉起来才能运行。

```mermaid
flowchart LR
    subgraph 环形依赖 [❌ 循环依赖 (严重缺陷)]
        A1["包 A"] --> B1["包 B"]
        B1 --> C1["包 C"]
        C1 --> A1
    end

    subgraph 解环方案 [ 解环策略：抽取抽象 / 接口下沉]
        A2["包 A"] --> D2["新抽象包 D (接口)"]
        B2["包 B"] --> D2
        C2["包 C"] --> D2
    end
```

### 打破循环依赖的两种标准手术刀：

#### 手术刀 1：依赖倒置原则 (DIP) + 接口隔离 (ISP)
* 如果类 A 依赖类 B，类 B 又因某种回调依赖类 A：
  - 在包 A 或独立接口层定义接口 `IA`；
  - 类 B 只依赖接口 `IA`；
  - 类 A 实现 `IA` 并直接调用 B。通过依赖反转消除循环链路。

#### 手术刀 2：提取公共核心包 (Extract Common Package)
* 如果包 A、B、C 形成环状依赖，找出引起循环的共同底层实体/数据传输对象（DTO），剥离出来放入一个新的底层包 D。
* 原先的三个包全部单向依赖于包 D，将环形网状依赖降级为严格分层的单向无环拓扑。
