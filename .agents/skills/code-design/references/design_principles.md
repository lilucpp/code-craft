# 面向对象演进式设计准则 (Design Principles)

## 一、 职责分配法则：从坏味道反推好设计

《重构》通过反面教材给出了职责分配最敏锐的标准：

### 1. 职责集中度（内聚性）
- **判定标准**：变化发生时的影响范围。
- **良性设计**：一种业务变化只引起一个模块修改；一个模块的修改只由一种业务诉求驱动。
- **坏味道警戒**：
  - 发散式变化 (Divergent Change) 提示模块职责过多，应提炼类 (`Extract Class`)。
  - 霰弹式修改 (Shotgun Surgery) 提示职责过度分散，应搬移函数与字段 (`Move Method / Field`)。

### 2. 依赖边界（耦合度）
- **迪米特法则（最少知识原则）**：
  - 模块不应了解所交互对象的深层内部结构。
  - 避免 `order.getCustomer().getAddress().getCity()`，重构为 `order.getCustomerCity()`。
- **特征依恋消除**：
  - 如果一个方法 80% 的计算都在操作另一个类的数据，此方法应当搬移到目标类中。

## 二、 继承体系的正确打开方式

### 1. 继承的真正目的：为了多态，而非仅仅为了代码共享
- 很多初学者误用继承仅仅是为了省写几行复用代码，导致父子类强绑定，产生“被拒绝的遗赠 (Refused Bequest)”。
- 如果父类的很多方法在子类中毫无意义甚至抛异常，果断使用**以委托取代继承 (Replace Inheritance with Delegation)**。

### 2. 平行继承体系的警惕
- 如果每当为抽象类 `Tool` 新增一个子类 `Pen` 时，就不得不为另一个抽象类 `Config` 新增一个对应的 `PenConfig`，说明两个体系高度耦合。
- 应通过让一个体系持有另一个体系的引用，将平行继承折叠为一个统一的委托结构。

## 三、 数据封装与强类型领域建模

### 1. 摆脱基本类型偏执 (Primitive Obsession)
- 错误示范：到处使用 `int code`, `string telephone`, `double price`。
- 正确设计：
  - 手机号封装为 `PhoneNumber` 类，内部自带格式校验；
  - 金额与货币封装为 `Money` 对象，保证不允许不同货币直接相加；
  - 不仅提升了安全性，而且消除了跨层重复校验。

### 2. 封装集合与防御性拷贝
- 类内部持有的 List / Map / Set，绝不直接通过 getter 返回原生引用。
- 必须返回不可修改的包装视图（如 `Collections.unmodifiableList`）或拷贝，提供专用的添加/移除方法。
