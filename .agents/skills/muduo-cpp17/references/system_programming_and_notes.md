# Linux 多线程系统编程精要与 C++ 工程心得

提炼自《Linux 多线程服务端编程》第 4 章（C++ 多线程系统编程精要）、第 11 章（反思 C++ 面向对象）与第 12 章（C++ 经验谈），聚焦多线程系统陷阱与日常编码原则。

---

## 1. 多线程与 Linux 系统调用铁律（第 4 章）

1. **多线程与 `fork()` 禁区（4.9 节）**：
   - 多线程进程中**严禁在运行期直接调用 `fork()`**。`fork()` 只复制调用线程，其他线程在瞬间持有的锁（含 glibc `malloc` 内部锁、日志锁）在子进程中处于永久锁定态，子进程任何动态内存分配或加锁都会死锁。
   - **合规做法**：仅在创建任何工作线程前 `fork()`；若运行期需拉起外部进程，使用 `posix_spawn()`（或 `reproc++`），或 `fork()` 后只调异步信号安全函数并立即 `execve()`。
2. **多线程与信号处理（4.10 节）**：
   - 在多线程程序中不要用传统异步 `signal()`/`sigaction()` 回调处理业务逻辑（极易因调用非 async-signal-safe 函数而死锁或破坏堆）。
   - **合规做法**：在主线程启动工作线程前用 `pthread_sigmask` 屏蔽信号，由专用线程调用 `sigwait()`，或使用 **`signalfd()`** 将信号转为同步可读事件纳入事件循环。
3. **统一事件源（4.11 节）**：
   - 优先使用 `eventfd`（跨线程唤醒）、`timerfd`（精确定时）、`signalfd`（信号同步化），把异步事件全部收敛为统一的文件描述符事件流。
4. **线程标识与日志（4.4~4.5 节）**：
   - 缓存 `syscall(SYS_gettid)` 到 `thread_local`（`__thread`）中，避免每次打日志或断言都陷入内核态；切忌跨线程直接复用 `pthread_t` 作全局唯一可读 ID。

## 2. 编码原则与 C++ 工程取舍（第 11~12 章）

1. **值语义（Value Semantics）优先于过度引用（11.7 节）**：
   - 值语义对象（可拷贝、生命周期自包含，如 `Date`、`Timestamp`、小配置结构）天然免于悬空指针与跨线程生命周期纠缠；
   - 只有在明确需要“身份唯一性”（如连接、线程池、文件句柄）时才使用对象语义（禁止拷贝，配合智能指针管理）。
2. **避用 `iostream` 承担高频格式化与日志（11.6 节）**：
   - `iostream` 的格式状态（如 `std::hex`）是粘滞的易造成后续输出污染，且在多线程下流锁开销与虚调用过多；
   - 高性能日志与格式化优先使用定长栈缓冲、`snprintf` 或 C++20 `std::format` / `fmt`。
3. **禁止重载全局 `::operator new()`（12.2 节）**：
   - 在实际工程中极易与第三方库或定制内存分配器（`jemalloc` / `tcmalloc`）冲突；如需定制内存池，应采用类作用域 `operator new` 或自定义 Allocator。
4. **“朴实”的 C++ 设计与原则总结（11.1、12 章）**：
   - **不炫技**：不用异或交换变量（`a ^= b ^= a ^= b`，同一对象自交换直接归零出错）；
   - **远离隐晦未定义/实现定义行为**：注意带符号整数除法/取余的跨标准差异、避免依赖静态全局对象跨翻译单元初始化顺序（改用函数内局部静态单例）；
   - **显式优于隐式**：禁止 C 风格强转，谨慎使用隐式转换构造函数（单参构造默认加 `explicit`）。
