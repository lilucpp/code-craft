# 自由度分级与脚本安全护栏设计

> 依据 Anthropic 官方规范中关于“自由度（Degrees of Freedom）与任务脆弱性匹配”的设计原则。

---

## 1. 自由度与任务特征矩阵

编写技能时最关键的工程决策之一，是给 Agent 多大的自由度。

```mermaid
quadrantChart
    title 自由度与任务特征象限图
    x-axis 低脆弱度(安全) --> 高脆弱度(危险/易错)
    y-axis 低可变性(固定模式) --> 高可变性(依赖上下文)
    quadrant-1 启发式检查清单 (高自由度)
    quadrant-2 参数化模板与脚本 (中自由度)
    quadrant-3 严格锁定硬脚本 (低自由度)
    quadrant-4 纯自动化沙箱单例 (极低自由度)
```

| 自由度等级 | 适用任务特征 | 交付形式 | 典型示例 |
| :--- | :--- | :--- | :--- |
| **高自由度 (High)** | 任务依赖上下文理解，存在多种有效解法，需模型综合权衡 | 文本指导原则、思考维度、启发式清单 | 架构设计、代码审查、坏味道识别、RFC 编写 |
| **中自由度 (Medium)** | 流程大体固定，但参数、格式或部分分支需根据场景微调 | 伪代码骨架、带默认参数的通用模板/函数 | 报表生成、数据清洗管道、多格式导出脚本 |
| **低自由度 (Low)** | 任务脆弱易错、顺序绝对不可颠倒、涉及数据安全或关键配置 | 硬性脚本、固定命令序列、明确禁止参数修改 | 数据库迁移脚本、崩溃安全原子写四步法、静态分析 |

---

## 2. 低自由度任务的护栏设计标准

对于低自由度任务，如果只用自然语言提示（如“请按顺序小心执行这几步”），Agent 在面临长对话或注意力分散时可能跳步或改动参数。

### 必须遵循的工程护栏：
1. **将复杂操作沉淀为独立脚本**：
   - 严禁让 Agent 在命令行手动拼接包含逻辑判断的长链命令（如 `cmd1 && (cmd2 || cmd3) | awk ...`）；
   - 封装为 `scripts/run.sh` 或 Python 脚本，并在脚本内部严格开启 `set -euo pipefail`。
2. **显式约束指令**：
   在 `SKILL.md` 中以粗体或代码块形式明确指令：
   ```bash
   ./scripts/run_check.sh --mode=diff
   ```
   *“运行上述精确命令，严禁修改参数或额外添加非必要 flag。”*
3. **输出可验证的明确反馈**：
   脚本必须包含状态自检，若失败直接输出具体的修复建议（如缺少工具时直接打印发行版安装命令），而不是让 Agent 猜报错原因。

---

## 3. 高自由度任务的结构化设计标准

对于高自由度任务，如果指引过于空泛（如“请审查代码并提出建议”），Agent 容易给出泛泛而谈的套话。

### 必须遵循的结构化要求：
1. **提供多维核对清单（Checklist）**：
   例如 `code-review` 技能，明确列出：架构分层违规、22 种特定坏味道、并发竞态、内存隐患。
2. **强制“双模式”或“步骤化推理”**：
   - 第一步：列举观察到的具体事实与代码行号；
   - 第二步：指出违反的具体软件工程原则（如 SRP、OCP、DbC）；
   - 第三步：给出 Before vs After 重构示例代码。

## 4. 错误驱动棘轮原则（Error-Driven Correction / Slop-to-Rule Ratchet）

> **核心铁律**：不要在“如何写更长、更委婉的 Prompt”上内卷；把每一次对 AI 的吐槽，下沉为一条机器可强执行的硬约束。

### 4.1 确定性下沉阶梯（按优先级从高到低）
当发现 Agent 反复犯同一类错误（Slop）时，**禁止优先往 `GEMINI.md` / `AGENTS.md` / Always-On Rules 追加自然语言警告**，必须优先按以下阶梯固化：
1. **编译器与类型系统**：`-Werror`、C++17 `[[nodiscard]]`、`explicit`、`StrongType`、Typestate 状态机；
2. **AST 静态检查**：启用 `.clang-tidy` 对应规则并加入 `WarningsAsErrors`；
3. **构建边界与扫描脚本**：CMake `PUBLIC`/`PRIVATE` 隔离、`check_include_dag.py`、`lint_redlines.py`；
4. **自动化测试与不变式**：RapidCheck 属性测试、libFuzzer、故障注入、ASan/UBSan/TSan 压测；
5. **Markdown 规则（兜底）**：仅保留静态工具与测试无法自动判定的高层设计哲学与协作准则。

### 4.2 新 Lint 准入四步路由与复杂度冻结（防正则脚本膨胀）
严禁使用 Python 正则脚本模拟 C++ AST 或做基于变量名猜测的算术/数据流推导。新增任何检查规则必须按以下四步分流：
1. **先查 AST 工具**：先运行 `clang-tidy --list-checks` 或查编译器 `-W...`；凡 AST/符号执行可覆盖的，必须配置到 `.clang-tidy`；
2. **模块依赖拓扑**：凡涉及目录分层、`#include` 环路与 `detail/` 隔离的，必须配置到 `.arch-boundaries.json` / `check_include_dag.py`；
3. **词法红线冻结（`lint_redlines.py`）**：仅允许收录**纯固定 API 名称或固定字面量黑名单**（由 `scripts/self_test.sh` 强制锁定 **$\le 5$ 类 `rule_id` 且总行数 $\le 380$ 行**）；
4. **复杂语义与协议不变式**：凡涉及协议校验范围、反序列化上界（`len > size - offset`）、锁序拓扑等，一律写入 `coding-standards.md`（1 行事前生成心智）+ `cpp-verification-playbook`（Gate 1 必测 & Gate 3 盲审）。

### 4.3 常驻规则“事前心智 + 事后兜底”平衡（Always-On Context Hygiene）
* 常驻规则（如 `coding-standards.md`）应剥离工具配置细节（如 `.clang-format` 的 YAML 键名），但**必须保留高浓缩的定量生成心智**（如“函数 20~30 行/硬上限 60 行、入参 $\le 3$、嵌套 $\le 3$ 卫语句平铺”），以提高模型第一次生成命中率（First-Pass Yield），再由 Lint 提供 100% 确定性兜底。
