# Bill Karwin《SQL 反模式》全景核心观点与治理指南

> 涵盖逻辑设计、物理设计、查询与应用开发全部核心反模式

---

## 一、 逻辑型数据库设计反模式 (Logical Antipatterns)

### 1. 乱穿马路 (Jaywalking)
* **表现**：在单列中用逗号分隔存放多个 ID 或标签（如 `tags: "1,2,5"`）。
* **破坏**：破坏第 1 范式；无法添加外键约束；`LIKE '%,2,%'` 触发全表扫描；无法做 COUNT 聚合；修改数据有并发写覆盖风险。
* **正解**：创建关联交叉表（Intersection Table / Join Table），双向主外键与复合索引。
* **合理例外**：极少修改、纯前端只读展示、不需要在 SQL 中被过滤或聚合的文本块。

### 2. 单纯的树 (Naive Trees)
* **表现**：仅存储 `parent_id` 的邻接表（Adjacency List）。
* **破坏**：深层多级祖先或子孙查询必须使用性能低下的递归 CTE 或嵌套自连接；删除非叶节点导致孤儿断裂。
* **四大方案权衡**：
  1. **邻接表 (Adjacency List)**：仅存 `parent_id`。适合极浅层级（层级 $\le 2$），插入快但查子树极慢。
  2. **路径枚举 (Path Enumeration)**：存 `/1/4/12/`。便于 `LIKE '/1/4/%'` 查子孙，但有长度上限且无法做外键约束。
  3. **嵌套集 (Nested Sets)**：`nsleft` 与 `nsright` 左右值编码。查子树极快（`BETWEEN`），但插入/删除任何节点都需要批量更新半张表的序号，写放大极其严重。
  4. **闭包表 (Closure Table，最推荐)**：维护独立路径表 `(ancestor_id, descendant_id, depth)`。查询任意子树退化为单表简单 JOIN，增删极其平滑，兼具灵活性与高性能。

### 3. 需要 ID (ID Required / 伪键滥用)
* **表现**：盲目为每一张表都增加自动递增的 `id` 代理主键。
* **破坏**：在多对多交叉表上强加 `id` 毫无意义，常因遗漏 `UNIQUE(a_id, b_id)` 导致脏数据；多层关联产生无谓的额外 JOIN。
* **正解**：交叉表直接使用联合主键 `PRIMARY KEY (a_id, b_id)`；强自然键表（如 ISO 国家代码、唯一编码）直接使用自然主键。

### 4. 不用钥匙的入口 (Keyless Entry / 丢弃外键)
* **表现**：因害怕 DDL 麻烦或所谓“性能损耗”而在物理表上完全摒弃外键约束。
* **破坏**：孤儿记录蔓延；应用层必须充斥大量防御性校验；级联删除手工实现极易漏删。
* **正解**：在单机关系数据库中强制启用外键约束，将数据完整性下推到数据库底层守护；仅在极端分布式分库分表边界才上移。

### 5. 实体-属性-值 (Entity-Attribute-Value, EAV)
* **表现**：用通用三元组表 `(entity_id, attr_name, attr_value)` 存放所有动态扩展字段。
* **破坏**：所有类型全部退化为裸字符串，失去类型系统校验；无法设置 `NOT NULL`；查询完整对象需要疯狂自连接（Self-Join 笛卡尔积）。
* **正解**：单表/类表继承结构，或采用现代半结构化 `JSONB` 配合**虚拟生成列（Generated Column）及 B-Tree 索引**。

### 6. 多态关联 (Polymorphic Associations)
* **表现**：子表定义 `parent_id` 和 `parent_type: "orders" | "users"`，试图关联多张异构父表。
* **破坏**：破坏关系完整性，无法声明物理外键约束；JOIN 查询必须依赖动态拼接。
* **正解**：为每个关联父表建立单独的关联交叉表，或创建抽象公共超类表。

### 7. 多列属性 (Multicolumn Attributes)
* **表现**：在表中定义 `tag1, tag2, tag3` 或 `phone1, phone2`。
* **破坏**：查询必须 `WHERE tag1=? OR tag2=? OR tag3=?`；扩充第 4 个标签必须修改 Schema 锁表；空列浪费。
* **正解**：规范化为一对多子表。

### 8. 元数据分裂 (Metadata Tribbles)
* **表现**：按年份/月份手工切表（`orders_2024`, `orders_2025`）。
* **破坏**：跨表统计需要巨型 `UNION`；表元数据缓存崩溃；每年都要跑定时任务建表。
* **正解**：采用数据库原生水平分区（Partitioning by RANGE/LIST/HASH），对外保持单表逻辑透明。

## 二、 物理型数据库设计反模式 (Physical Antipatterns)

### 9. 取整错误 (Rounding Errors)
* **表现**：使用 `FLOAT / DOUBLE` 存储财务与金额。
* **破坏**：IEEE 754 二进制截断误差（`0.1 + 0.2 != 0.3`），多次累加出现账目漂移。
* **正解**：强制使用 `DECIMAL(18, 4)` 精确定点数。

### 10. 每日新花样 (31 Flavors / ENUM 陷阱)
* **表现**：使用 `ENUM('A', 'B', 'C')` 限定取值。
* **破坏**：增加枚举项需要昂贵的 DDL 锁表；无法支持多语言展示；不同引擎迁移不兼容。
* **正解**：小码表（Lookup Table / Reference Table）配合外键约束。

### 11. 幽灵文件 (Phantom Files)
* **表现**：仅在数据库存本地文件路径（`"/data/avatar.png"`）或将几十兆视频直接塞入数据库 BLOB。
* **破坏**：仅存路径导致事务与文件不同步（数据库回滚了但文件已删除）；存巨型 BLOB 导致数据库缓存池迅速耗尽。
* **正解**：< 1MB 小图与敏感元数据用 BLOB 保证事务一致性；大文件放入对象存储（S3/OSS），数据库只存不可变 Content Hash 与访问 URI。

### 12. 乱用索引 (Index Shotgun / 索引霰弹枪)
* **表现**：盲目为每一个字段都分别建单列索引，或者完全凭感觉不建索引。
* **破坏**：写入一条记录触发多个 B-Tree 页面分裂与写放大；多条件查询依然无法利用联合优势。
* **正解**：MENTOR 法则——针对前 20% 高频慢 SQL 定制复合索引；定期清理冗余前缀索引。

## 三、 查询与应用开发反模式 (Query & App Antipatterns)

### 13. 对未知的恐惧 (Fear of the Unknown / NULL 陷阱)
* **表现**：将 NULL 当作具体值比较，或滥用空串/0 代替 NULL。
* **破坏**：SQL 三值逻辑（True, False, Unknown）；`WHERE col NOT IN (1, 2, NULL)` 导致查询结果恒为空集（整表记录消失）。
* **正解**：外键与枚举字段强制 `NOT NULL DEFAULT ...`；子查询存在性校验强制使用 `NOT EXISTS` 代替 `NOT IN`。

### 14. 模棱两可的分组 (Ambiguous Groups)
* **表现**：在 `GROUP BY` 中查询未被聚合的非分组列（违反单值规则）。
* **破坏**：不同数据库随机返回第一行数据，导致隐蔽的逻辑 Bug。
* **正解**：所有 `SELECT` 非聚合列必须属于 `GROUP BY`，或改用窗口函数 `ROW_NUMBER() OVER (...)`。

### 15. 随机选择 (Random Selection)
* **表现**：`SELECT * FROM t ORDER BY RAND() LIMIT 1`。
* **破坏**：整表逐行计算随机数并执行全表内存/磁盘临时排序，大表必导致 CPU 100% 或超时。
* **正解**：随机抽取连续主键范围偏移，或由应用层生成随机 ID 进行点查。

### 16. 可怜人的搜索引擎 (Poor Man's Search Engine)
* **表现**：用 `LIKE '%keyword%'` 做全文搜索。
* **破坏**：左通配符完全破坏 B-Tree 首字符物理排序，强制全表扫描。
* **正解**：数据库内建全文索引（Full-Text Index）或挂载外部搜索引擎（Elasticsearch）。

### 17. 意大利面条式查询 (Spaghetti Query)
* **表现**：试图用一条极其庞大的单一 SQL 完成所有维度的联表统计与业务计算。
* **破坏**：产生巨型笛卡尔积，执行计划混乱无法走最优索引。
* **正解**：分而治之，拆分成小而快的步骤，让数据库做纯检索，利用应用层多核做聚合。

### 18. 隐式的列 (Implicit Columns)
* **表现**：生产代码滥用 `SELECT *`。
* **破坏**：消耗多余网络 I/O；**彻底破坏覆盖索引能力，强制数据库进行回表随机 I/O**；表加字段直接破坏基于列序号的代码绑定。
* **正解**：按需明确列出所需字段。
