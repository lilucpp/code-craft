# Stack Overflow 黄金提问与排障规范 (How to Ask & MRE)

> 整理自全球最大开发者社区 Stack Overflow 官方指南《How do I ask a good question?》（https://stackoverflow.com/help/how-to-ask）。

在技术排查、社区求助、GitHub 提报 Issue 或跨团队协作中，**一个糟糕的问题会浪费所有人数小时的无效沟通，而一个高水准的问题往往在编写完成的瞬间就已经解决了一半**。

---

## 一、 MRE 原则：最小可复现示例 (Minimal, Reproducible Example)

在展示有问题的代码时，必须严格遵守 MRE 三要素：

```
[Minimal 最小化]     ：剔除 90% 不相关的业务逻辑，只保留复现 Bug 的骨架
         +
[Complete 完整性]    ：包含所有必要的 import、初始化数据与调用，他人可直接运行
         +
[Reproducible 可复现]：在空白环境中执行必能稳定复现出该异常现象
```

### 1. Minimal（最小化）
* **剔除业务噪音**：将几千行的业务控制器，简化为几十行的最小独立脚本；
* **二分注释法**：每次注释掉一半不相干的代码，如果 Bug 依然能复现，说明被注释的部分可以安全移除；
* **安全保护**：永远不要在公开提问或 Issue 中泄露公司私有代码、密码、密钥或真实生产数据。

### 2. Complete（完整自洽）
* 避免贴出缺少前置变量声明、缺少结构体定义的代码碎片；
* 必须是一个**“开箱即运行”**的最小独立文件。

### 3. Reproducible（百分之百可复现）
* 指明运行的环境版本（操作系统、语言版本、依赖库精准版本号）；
* 提供一组能触发该 Bug 的确定性输入参数。

## 二、 提问与 Issue 撰写五大纪律

### 1. 自解释的标题（Title）
* **原则**：假装你正在和一个忙碌的同事面对面，必须用一句话说清你的问题与核心特征。
* **正反案例对比**：
  * ❌ *Bad*: “C# 求助，计算结果不对”
  *  *Good*: “为什么输入全为整数时，C# 使用 float 代替 int 会产生精度差异？”
  * ❌ *Bad*: “[Python] 为什么代码报错？”
  *  *Good*: “在多线程环境中调用 `list.append()` 为何会导致 `IndexError`？”

### 2. 代码前先讲清背景与情景 (Context Before Code)
* 第一段不要直接扔代码；
* 用 2~3 句话说明：你的业务目标是什么？你在什么场景下触发了问题？你自己尝试了哪些解决方式但失败了？

### 3. 严格对比预期行为与实际表现 (Expected vs Actual)
必须显式分开两段内容：
* **预期行为 (Expected Behavior)**：我期望函数返回什么值，或者系统处于什么状态；
* **实际表现 (Actual Behavior)**：实际输出了什么？是否崩溃？（完整贴出控制台的异常调用栈 Stack Trace）。

### 4. 严禁使用图片/截图展示文本内容
* **永远不要截取代码、日志或报错信息的图片**！
* **原因**：图片无法被搜索引擎索引、无法复制运行、在移动端极难辨识；
* 所有的代码、终端日志一律使用 Markdown 代码块（` ```lang `）完整贴出纯文本；图片仅限于展示 UI 渲染错位或拓扑图。

### 5. 列出已尝试的排查步骤 (What I've Tried)
* 说明自己已经排查过哪些假设，避免回答者重复建议你已经试过的无效途径。
