# 编码规范与设计底线准则 (Clean Coding Standards)

> 本规范基于马丁·福勒《重构》核心思想与现代软件工程最佳实践，作为日常开发、编码和审查的通用准则。

---

## 1. 核心设计原则

- **单一职责原则 (SRP) 与 KISS**：
  - 一个类或函数应该只有一个引起它变化的原因；简单到只做一件事并做到极致。
  - 严禁出现既包含高层业务调度、又包含底层 I/O、协议解析的大杂烩函数或类。
- **极致解耦与依赖标准 (DIP)**：
  - 模块间绝不直接依赖具体实现，必须依赖抽象标准、接口定义或标准数据流协议。
- **机制与策略分离 (Separation of Policy and Mechanism)**：
  - 核心计算与数据模型（机制）保持纯粹、通用与无状态；界面呈现与分发逻辑（策略）外置。
- **表示原则与数据驱动 (Data-Driven)**：
  - 把逻辑叠入数据。面对复杂条件分派，优先使用分派表（Dispatch Table）或状态机表，消除多层 `if-else / switch`。
- **演进式设计与 YAGNI**：
  - “事不过三，三则重构”。不要为“未来可能出现”的虚构需求预留过多的抽象层和通用钩子（杜绝*夸夸其谈未来性*）。
- **组合优于继承 (Composition over Inheritance)**：
  - 优先通过委托与组合实现特性复用；只有在存在严格的“Is-A”语义、且子类完全复用父类行为时才使用继承。
  - 避免深层继承树（继承深度建议 <= 3 层），必要时使用“以委托取代继承”。
- **最少知识原则 / 迪米特法则 (Law of Demeter)**：
  - 避免出现连续调用链 `a.getB().getC().action()`；通过在宿主对象上提供门面/委托方法（*隐藏委托关系*）。
- **契约式设计 (DbC) 与 关注点分离 (SoC)**：
  - 方法入口明确前置条件约束，出口保证后置返回承诺；业务逻辑与横切技术关注点解耦。
- **惯例优于配置 (CoC)**：
  - 遵循业界主流目录与命名规范作为默认规则，非必要不增加胶水配置文件。
- **无环依赖原则 (ADP)**：
  - 包与模块间依赖必须为有向无环图 (DAG)，严禁出现循环依赖；若出现循环，必须通过 DIP 抽象或抽取公共层解除。

## 2. 函数级编码规范

1. **短小与单一抽象层级 (SLAP)**：
   - 单函数长度建议控制在 **20~30 行** 以内。
   - 函数内部所有语句应处于同一抽象层级；底层细节应提炼为自解释的私有子函数。
2. **卫语句优先 (Guard Clauses)**：
   - 杜绝多层嵌套的 `if-else`。优先使用卫语句对异常、边界条件进行先行检查并立即 `return`，让正常业务主干平铺。
3. **参数控制**：
   - 单函数入参尽量 **<= 3 个**。
   - 当参数列表 >= 4 个，或者某些参数总是成对出现时，必须封装为**参数对象 (Parameter Object)** 或结构体。
4. **无副作用与查询修改分离 (CQS)**：
   - 查询函数（Query）不应改变对象状态；有副作用的修改函数（Modifier）尽量不返回复杂状态，将查询与修改彻底解耦。
5. **移除控制标记 (Control Flags)**：
   - 避免使用布尔标记变量在循环体或复杂分支中跳转，使用 `break`、`continue` 或提前 `return`。

---

6. **I/O 流分离与缄默原则**：
   - `stdout` 仅承载机器消费的纯数据负载；所有日志打点、诊断信息、警告进度一律写入 `stderr`。
   - 程序执行成功且无须返回数据时，保持沉默，绝不输出无意义的交谈文本。

## 3. 命名、数据与注释规范

1. **意图自解释命名**：
   - 变量、函数、类名必须表达“做什么”或“是什么”，严禁使用 `data`, `info`, `temp`, `flag`, `item1` 等无意义缩写。
2. **注释作为除臭剂 (Comments as Deodorant)**：
   - 当感觉需要写一行注释来解释一段代码在做什么时，**优先将这段代码提炼为一个命名自解释的小函数**。
   - 注释只记录**“为什么这样做（业务原因、背景陷阱、底层约束）”**，绝不复述“做了什么”。
3. **消除魔法数 (Magic Numbers)**：
   - 禁止在逻辑中直接出现裸露的数值或字符串字面量，必须提取为自解释的常量枚举或符号常量。
4. **数据自封装与值对象**：
   - 禁止直接向外暴露类的裸字段；集合字段必须返回只读包装或副本（*封装集合*）。
   - 带有特定业务约束的数据组（如货币与金额、起止时间区间），封装为不可变的值对象。

## 4. 系统级数据布局与存储底线 (Systems Data & Storage Standards)

1. **结构体降序对齐与消除 Padding**：
   - 结构体成员严格按照 **8 字节 $\to$ 4 字节 $\to$ 2 字节 $\to$ 1 字节** 降序排列，消除编译器插入的隐式填充空洞，最大化 CPU L1 缓存利用率。
2. **多核伪共享防御 (False Sharing)**：
   - 跨 CPU 核心频繁写操作的独立变量，强制使用 `alignas(64)` 隔离，杜绝 CPU 缓存行颠簸（Cache Line Bouncing）。
3. **关键标量强类型化 (Strong Typing)**：
   - 杜绝裸整数表达核心 ID（`UserId`, `SessionId`）与单位物理量（`ByteOffset`），使用编译期零开销的强标量包装。
4. **编译期类型状态机 (Typestate)**：
   - 具备多阶段生命周期的资源（连接、事务句柄），将状态提升为类型参数，在编译期拦截时序调用错误，省去运行时 `if-check`。
5. **本地文件持久化崩溃安全 (Crash-Consistency)**：
   - 遵循 OSDI 2014 顶会规范，文件原子落盘强制执行四步法：`写入临时文件 -> fdatasync 刷盘 -> 原子 rename 替换 -> 父目录 fsync`，彻底杜绝断电导致文件损坏或变成 0 字节。
6. **关系数据库存储规范 (SQL Craft)**：
   - 涉及到金额、利息、账务字段，强制使用 `DECIMAL(18, 4)` 精确定点数，严禁使用 `FLOAT/DOUBLE`；
   - 严禁逗号分隔存储多值列表（乱穿马路），多对多建立关联交叉表；深层树状结构采用闭包表（Closure Table）；
   - 复合索引严格遵循“等值列在前、范围列在后”；千万级大表翻页主动采用 Keyset 寻址分页（Seek Method 替代 OFFSET）。

## 5. C++ 语言专项与静态分析底线

1. **代码风格与排版基准**：
   - 严格遵循 Google C++ 规范基线，并应用三处核心约束：
     * **指针与引用右对齐**：`PointerAlignment: Right`（如 `char *p; const string &ref;`）；
     * **禁用指针推断**：`DerivePointerAlignment: false`（彻底消灭歧义）；
     * **行宽上限放宽**：`ColumnLimit: 120`（提升现代泛型与模板代码的可读性）。
2. **增量治理法则 (Boy Scout Rule)**：
   - 面对历史老项目，严禁盲目执行全量格式化；**必须使用增量模式（如 `clang-format-diff` 与 `run_check.sh --mode=diff`）仅对当前改动行/改动文件执行格式化与静态检查**。
3. **三方库三重隔离**：
   - 在 `.clang-format-ignore` 中显式排除 `third_party/**` 与 `build/**`；
   - 在 `.clang-tidy` 中通过 `HeaderFilterRegex` 屏蔽非业务源码头文件；
   - 在 CMake 中通过 `SYSTEM` 关键字引入外部依赖，压制第三方内部警告。
4. **编译警告等同错误 (Warnings as Errors)**：
   - 开启 `-Wall -Wextra -Wpedantic -Wconversion -Wshadow -Wnon-virtual-dtor -Wold-style-cast` 并视警告为错误。

## 6. 实证与安全底线

- **补救原则与快速失败 (Rule of Repair / Fail-Fast)**：
  - 严禁静默吞掉异常（如空 `catch` 或忽略系统调用错误码）。一旦遇到不可恢复异常，立即退出崩溃并向 `stderr` 打印足量上下文。
- **写 Demo / 测试验证不确定性**：
  - 遇到歧义、边界情况、锁与并发机制时，严禁凭空推测，必须编写最小测试用例实际运行验证。
- **小步微调 (Baby Steps)**：
  - 修改代码坚持最小变更集，每次修改保持可编译、可测试状态。
- **提交确认**：
  - 代码改动后严禁私自自动执行 Git Commit，必须向用户汇报改动并等待用户明确确认。
